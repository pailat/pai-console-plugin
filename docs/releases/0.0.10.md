## Changes since 0.0.9

The synthetic platform-admin corporate inventory contains **304 tools: 122 reads and 182 writes**, with 24 additions and no removals. Upstream declares 306 names; the two proposal response tools remain client-only. A person's actual tool availability still depends on effective permissions.

- API Design: eight `api_design_*` tools, OpenAPI rules and findings, revision-aware saves, ERD scaffolding, saved page blocks and a network-free mock. Generic Knowledge writes do not replace API Design operations.
- Pai Agent: attachments, anchored comments, traces and human approval responses; guidance for credit-budget endings and failed turns. An agent never approves its own pending action.
- Resources: organization General resources, explicit project scope, resource origins and client-visible embed projections. Identical names across projects are resolved by identity and scope.
- Knowledge: appearance operations and edge history, plus the internal `api` kind and its dedicated workflow.
- Products and schedules: internal release plans, advisory definition evidence, human-only PRD version confirmation, time flags and effort estimates. Release plans never deploy software.
- CRM: the `{opportunity, discovery}` loss result, literal `kept` outcomes, title conflicts, task archiving behavior and permission-driven discovery. Do not close a retained Discovery project to work around an authorization result.
- Organizations: archive/restore with exact-name confirmation, platform permissions and active-subscription refusal. Archiving is reversible but hides the organization for everyone until restored; no hard-delete tool is introduced.
- Installation: existing Claude names, agents, configurable corporate endpoint and production write confirmations are preserved. Codex staging/develop/production packages remain generated from shared sources with separate adapters and native approval policies.

See the [upstream integration checkpoint](../upstream-sync-0.0.10.md) for individual tools, source behavior and evaluation history, and [verification](../verification.md) for the checks actually executed.

## What this release does not establish

- No live Pai write, OAuth sign-in, production approval prompt, desktop hook trust or infrastructure change is verified by source regeneration or mocked tests.
- The recorded behavioral evaluations use local stand-ins and probabilistic graders. Earlier scores are historical evidence, not a new run during release preparation.
- PR #263's deployment and security acceptance remain upstream responsibilities. This plugin release does not close its pending staging checks or advisories.
- Updating a plugin does not switch the user's selected environment or authenticate a different endpoint. Reload/restart as required and verify the selected server with `whoami` before operations.

## Publication checklist

1. Review the release-preparation PR against plugin main and confirm that the Pai Portal head has not moved. If it moved, compare contracts and behavior again before publication.
2. Require byte-identical reference regeneration, example validation, generated-package reproducibility, English authoring checks, Python tests with available native probes, and all four Claude strict validations. Keep simulated and installed-client evidence distinct.
3. Merge the release-preparation PR only after review. Resolve the resulting main SHA explicitly; do not tag a stale feature branch or the earlier plugin checkpoint by assumption.
4. Verify that `v0.0.10` has not already been published and that the Claude manifest and every generated package still report 0.0.10. Retarget any draft release to the reviewed main SHA before publication.
5. Publish `v0.0.10` with these notes only after the release is accepted. Preparation may create a draft; it must not mark it as published or claim marketplace propagation.
6. After publication, check the tag/release commit and installed-client update behavior. Claude users update their existing marketplace plugin and reload plugins; Codex users refresh their existing marketplace source and update their selected package without implicitly switching environments.

No installed-client configuration, credentials, database, infrastructure, or production data is changed by this checklist.
